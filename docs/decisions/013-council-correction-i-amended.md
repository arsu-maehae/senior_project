# 013 — Council verdict: amend Correction I (cross-host link)

**Date:** 2026-11-10 · **Status:** accepted by the owner (2026-11-10, with two clarifications) · **Task:** T4 · Full five-adviser council (`.claude/skills/council`), brief confirmed by the owner. Supersedes the "UNDER REVIEW" mark from decision 011.

## Context
Correction I linked a cross-host hop by target 4624 (IpAddress, IpPort) ↔ source Sysmon 3 → ProcessGuid → session. The Sysmon configuration never logged SMB (decision 011, `docs/research/sysmon_config_check.md`). Measured evidence (`docs/research/data_reality.md`, log-check spec `00_log_check.md`): every scenario-account attack hop in S02–S07 t00 has exactly one account-consistent source session; SMB hops only by command line (tier B), WinRM hops also by port join (tier A, agreeing); S04's two tracks give 2 candidate sessions before and 1 after an account filter; in S06 a svc_backup agent acts with admin_it credentials, so only the Security 4648 bridge recovers the session; all SMB hops are NTLM by IP (no LogonGuid confirmation); RDP source side not measurable until S01 t01.

**Brief.** Decision: how to link cross-host hops when the source has no Sysmon 3 for SMB and only partial Sysmon 3 for WinRM/RDP. Stage: T7 stitch. Constraints: no re-runs; S01 t01 pending; t00 development, t01–t10 locked test set. Success: right source session per attack hop with candidate_count recorded, link accuracy vs keys (T7.6), S04 tracks never cross-linked. Owner's lean: decision 011. Owner's fear: several candidate sessions on EP-01, or the admin session linked instead of the attacker's in S04.

## Options considered
| Option | Pros | Cons |
|---|---|---|
| Keep Correction I as written | Locked rule unchanged | Cannot link any SMB hop in the collected data |
| Decision 011 with account as a required filter (owner's lean) | Simple; separates S04 tracks on t00 | Contradicts handoff_18.md:231 ("account as supporting check, not a required join condition"); the S04 split is a by-product of Option D; biases IdentityCoherence if identity reads the linked session |
| **Amended Correction I: target anchor + three source methods, account as supporting evidence (chosen)** | Uses every source signal (port, 4648, command line); every candidate recorded; identity decoupled from linking | Command-line join rests on Caldera naming targets by IP; 4648 coverage shown only in S06 |

## Decision (chairman's verdict, accepted)
- **THE CALL:** amend Correction I. Anchor = target 4624 + its session artefacts (5140/5145 and 4697 by SubjectLogonId; 7045 by time + binary file name). Source session by any of three methods, each its own `method`: (1) Sysmon 3 port join, tier A where logged (WinRM; RDP once S01 t01 exists); (2) source 4648 naming the target (gives SubjectLogonId directly); (3) Sysmon 1/4688 command line naming the target, boundary-aware. **Account is a supporting check, never a join condition**: every candidate session is emitted with `account_match` ∈ {direct, 4648, none} and `candidate_count` before/after; the tier uses it. Kerberos LogonGuid only confirms (none for NTLM SMB). A hop with no source candidate is kept as `target_only` (tier D).
- **Owner clarification 1:** IdentityCoherence uses only the moving account (target 4624) and the source host (by IP), never the linked session, so it is computed for every hop, including `target_only` hops. "Unlinked" affects path assembly and link tier, not identity. (CLAUDE.md "Identity input".)
- **Owner clarification 2:** limitation L11 — the command-line join works in the lab because the Caldera scripts name targets by literal IP; generalisation to real attackers is untested.
- **CONFIDENCE:** medium — consistent on all t00 attack hops and the two WinRM methods agree, but ~10 SMB hops, one trial per scenario, no answer keys, and target naming is a property of the tooling.
- **BIGGEST RISK:** on t01–t10 or with another operator, commands may not name the target, or several sessions may; S04 Track A → desktop session 0xd6398 (not agent 0x17b18) is unverifiable until T5; 4648 coverage: log-check LC-04h finds a 4648 naming the target in S03 (1/1 hops), S05 (1/3) and S06 (4/5), and none for any SMB hop by IP in S02, S04, S05 or S07 — those rely on the command line alone.
- **WHERE THE COUNCIL SPLIT:** account filter required (lean; implementer adviser before peer review) vs supporting (fact-checker, committee member, researcher; implementer changed after review); 4648 primary (researcher) vs evidenced only in S06 (others); generalisation (committee member: tooling artefact; kept as L11).
- **WHERE I MIGHT BE FOOLING MYSELF:** all evidence is t00 and the hop list comes from the measuring script; Option D makes accounts coincide by construction; "right session" is unverified until T5.
- **NEXT STEPS (implementer):** T7 spec with the link-row schema (hop_id, protocol, src/dst host, src_session_id + hex, accounts, method {sysmon3_port, source_4648, cmdline_target, target_only}, confirm {kerberos_logonguid, service_admin_write, none}, account_match, candidate_count before/after, time_delta_ms, confidence_tier, event_uids); move pure helpers from `src/log_check` into a shared module; first test on real S04 t00.
- **TEST IDEAS (tester):** S04 both tracks emit 2 candidates each with the right one `account_match = direct`; S06 hops linked by `source_4648`; S07 h2/h3 separated by service/binary name; a hop with no source evidence yields a `target_only` row; identity unchanged when the linked session changes.
- **KILL CRITERIA:** (1) with T5 keys on the development trials, if the best-tier source session is wrong for more than 1 SMB attack hop, drop source-session linking for SMB (target-only; identity still from account + host) and state it as a limitation; (2) on t01–t10, if more than 20% of attack hops have `candidate_count` > 1 after supporting evidence, report SMB links as tier C; (3) if a keyed hop whose source session runs under a different account than the 4624 account (credentials supplied for another account) has no 4648, drop 4648 as a method. (A `net use /user:` for the session's own account, as in S04 h3, is not such a hop.)

## Consequences
CLAUDE.md "Cross-host link" text replaced by the amended rule and a new "Identity input" line. T7 implements the three methods and the `target_only` row. Limitations L10 (decision 011) and L11 apply.

## Committee answer
**EN:** Our Sysmon never logged SMB, so we anchor each move on the target's logon and its share and service events and find the source session by port, by the explicit-credential event, or by the command that names the target; the account only supports the link, and identity is computed from the moving account and the source host, independent of which source session was chosen.
**TH:** Sysmon ของเราไม่ได้บันทึก SMB เราจึงยึดการเคลื่อนที่แต่ละครั้งกับ logon ฝั่งปลายทางและเหตุการณ์ share/service ของมัน แล้วหาเซสชันฝั่งต้นทางจากพอร์ต จากเหตุการณ์ใช้ credential แบบ explicit หรือจากคำสั่งที่ระบุชื่อเครื่องปลายทาง บัญชีเป็นเพียงหลักฐานเสริม และค่า identity คำนวณจากบัญชีที่เคลื่อนที่กับเครื่องต้นทาง โดยไม่ขึ้นกับเซสชันที่ถูกเลือก

## Appendix A — advisers' answers (anonymised as in the peer review)
A = fact-checker · B = committee member · C = implementer adviser · D = attacker · E = researcher (sources for E: docs/papers/HADES.pdf p.5, §V p.8; Microsoft Learn event-4648, event-4624).

### A
Blocking: (A2) the account filter is used as a REQUIRED join condition, but handoff_18.md:231 (Correction I) says "Treat account as a supporting check, not a required join condition"; accounts coincide only because of Option D (handoff 19.2, Correction H.4). The S04 2->1 split depends entirely on this filter, so it is a by-product of lab construction, not a property of the method. (A5) "Right session" cannot be verified: no T5 keys; S04 Track A links to 0xd6398 (admin desktop, type 11), not the admin_it agent session 0x17b18 - exactly the owner's fear. Assumptions: A1 attack commands name the target - PLAUSIBLE (all S02-S07 t00 attack hops; benign h1 hops have none; RDP unmeasured). A2 moving account = session account, 4648 covers explicit creds - PLAUSIBLE (lab only; 4648 completeness UNTESTED beyond S06). A3 t01-t10 behave like t00 - UNTESTED. A4 HADES links the same way - WRONG: HADES only links auth/logon logs by logon GUID (sec V p.8), claims one parent session (p.4-5) but publishes no source-session rule; both Correction I and decision 011 are our own method. A6 SMB links have independent confirmation - WRONG: SMB hops are NTLM by IP, no LogonGuid check.

### B
Examiner questions: (1) Why trust a command line? Encoded PowerShell, target lists from files, WMI/DCOM, impacket from an unlogged host; four hops (S04-S07 h1) already have no naming command and are called "benign-looking, cause not verified". (2) Is the account filter circular? Linking keeps only same-account sessions; Correction K then asks if that account had a session open on the source - the link step pre-selects part of the identity condition, inflating IdentityCoherence. (3) How many trials? One trial per scenario (t00), ~10 SMB hops, provisional windows, no approved keys; the 4648 bridge was added after seeing S06 fail - tuned on the same data that supports it. (4) "Right one each time" judged against what? The hop list comes from the same script; keys don't exist. (5) Generalisation: scripted Caldera `net use`/`sc.exe \IP` is the easiest case; PsExec, scheduled tasks, a human operator? Weakest answer: (1) - the only evidence is that the lab's Caldera scripts put literal IPs in commands, a property of the tooling, not of SMB lateral movement.

### C
Adopt the lean but split methods and tiers. Move pure helpers from src/log_check (matching, bridge, hop grouping, port_join, protocol label, collapse_processes, evaluate_hop, admin_write_sessions, dedup_services) into a shared src/linkcore/ with explicit parameters; src/stitch/ gets inputs (gated hops), target_side (5145/7045 tie, 4769 confirm), source_cmd, source_port, link.link_hop() -> LinkRow, writer with masking. Link row: hop_id, protocol, src/dst host, src_session_id + hex, accounts, method {sysmon3_port|cmdline_target|cmdline_4648|target_only}, confirm {kerberos_logonguid|service_admin_write|none}, candidate_count (+ before account filter), time_delta_ms, tier {A,B,B4648,C,D}, event_uids; one row per candidate; hops with no source session get a target_only tier-D row, never dropped. First test on real S04 t00: svc_backup 10:57:36.855 -> one row, session 0x17c46, cmdline_target, count 1 (2 before), tier B, delta ~906 ms, uids incl. UpdaterService 7045 and Stage.exe 5145; Track A -> 0xd6398; h1 -> target_only; confirm against T5 key. Hard parts: no gate yet (stub input), no Kerberos confirm for SMB, 4648 needs its own tier, shared agent session serves several hops, RDP waits for S01 t01. Effort ~4 days + 0.5 RDP.

### D
Failures only. (1) Benign admin_it SMB logons (S04-S07 h1) get no source session; if the scorer treats "unlinked" like "linked, identity 0" they may outrank real hops after merging - test on t01-t10. (2) Identity cannot separate S04 Track A from Track B (both 1, admin desktop 0xd6398 open at the dump); the S04 headline shows no separation; ties must not be broken arbitrarily. (3) Command-line join assumes one account-consistent session: two same-account sessions (admin desktop + admin agent) both running `net use \192.168.50.22` would give 2 after the filter; S07 h2/h3 come from one session 0x161a2 and are distinguishable only by the 7045 service name - links can swap. (4) The S06 4648 bridge is the only rescue for 1->0; fails if 4648 is missing or TargetServerName (hostname) doesn't match an IP-only command. (5) Time tolerance: offsets up to 4.5 s (ep-03), commands -3.1 s before the 4624; tolerance below 5 s or a skewed anchor host breaks it. (6) Missing Sysmon 1/4688 or commands via script/alias that don't name the host. RDP has no source evidence: first S01 t01 run is a risk.

### E
HADES (docs/papers/HADES.pdf) never uses a port join or Sysmon 3 [fact-check: overstated — HADES §V p.8 collects Sysmon logs and Fig. 3 p.4 has network-socket nodes; it describes no port join]: its cross-machine link is the target logon plus logon-session ID, and DC auth logs are linked to host logons by Logon GUID (sec V p.8); principle p.5: a target logon session "resulted from exactly one logon session" on the source; no SMB-specific source rule published. So Correction I's port join is our own rule; decision 011 stays consistent with the paper. Missed upside: Security 4648 (Microsoft Learn) carries SubjectLogonId, ProcessId/Name, TargetServerName, network address/port - a source-host event naming the session directly; it should be a PRIMARY link, not only a bridge. Microsoft's 4624 page warns NTLM logons may lack TCP/IP details: verify IpPort per trial, don't hard-code it as a key. Option C (layered, tiered): (1) target 4624 LogonId -> 5140/5145 and 4697 SubjectLogonId, 7045 by time + file name; (2) source 4648 (TargetServerName/IP, same account) -> SubjectLogonId, else Sysmon 1/4688 command line; (3) NTLM: DC 4776 as extra confirmation (UNVERIFIED in lab); (4) Sysmon 3 / port join = tier A where it exists; (5) tiers + candidate_count, keep every candidate. Amend Correction I to "target 4624 + target-side session artifacts <-> source session via 4648 or command line; port join raises the tier"; do not delete the port join.
