Five key attack hops go from tier B to D with no candidate session: s02-h1, s04-B-h1, s05-h1, s07-h-x and s07-h-y
(A, key_attack_hops). s03-h1 and s05-h2 stay at tier A.

On the hop reading, which maps key hops by target logons, the order of the key attack paths did not change. The
switch does change path assembly and the nodes each path holds, so this was not guaranteed in advance.

The node-based measures fall:
- In every attack trial, every node lost is a `source_evidence` node, and every lost key node is one of the key's
  agent process events (`agent_event_uids` / `agent_corroboration_4688_uids`), which only the command-line method
  attaches (decision 077).
- s03 shows the same pattern: its hop keeps a tier-A session but loses its two command-line evidence nodes.

The node rows in A's `headline_hop` table are node-based, labelled as such in their notes.

## Stated limits
- The development set is 9 trials, 5 of them keyed attack trials. Test trials repeat the same scenarios, so a test
  result would measure repeatability, not generalisation to new attacks (spec 05 §7.3).
- Inside one protocol, attack and benign paths have equal LengthScore and NodeScore, so their order comes from
  IdentityCoherence. The answer keys share that definition (Correction K, L-SC5).
- The answer keys are built from the same logs as the pipeline (020). The ablation is the one measure that removes
  the stitcher's use of that evidence.
